# Generate Book

Create a readable, project-specific learning book as one self-contained HTML file. Use everyday English for reader-facing explanations while preserving the technical reasoning. Match the Rust Book's standard of explanatory continuity: an entry-level reader should be able to follow how each new idea grows from an established example, predict the relevant behavior, and explain why it happens without needing a second, simpler explanation. Achieve that standard with original prose and project-specific examples; sentence length, chapter count, and a familiar-looking reader are not measures of comprehension.

## Ground it in evidence

- Inspect the project entry points, configuration, tests, existing documentation, and Git history before writing.
- Treat code and configuration as the authority for current behavior. Use the history to describe actual implementation steps only when it is available.
- If history is absent or incomplete, label the sequence as a suggested reconstruction from the current code. Do not invent dates, decisions, experiments, or author intent.
- Separate what the sources show from a reasonable explanation of why a choice helps. State uncertainty plainly.
- Derive dependency names and versions from manifests and lockfiles. Check external technical details against official documentation when the book needs them.
- Explain the end-to-end behavior in a useful order: the goal, the building blocks, important decisions, failure cases, and how to run or check the result. Define unfamiliar terms when they first matter.
- Prefer short code excerpts that illustrate a point. Use a complete listing only when it helps the reader see how the parts fit together. Keep examples consistent with the checked-in project.

## Keep the writing original

When a reference book is provided, study its broad teaching methods, such as introducing ideas gradually, using concrete examples, and pausing to check understanding. Do not reproduce its prose, distinctive voice, chapter order, named examples, or branded visuals. A user may ask to reuse a reference's general layout or interactions; follow that request while keeping the book's content and visual identity original. This applies to private and local-only output as well.

## Teach with a repeatable learning method

Apply every instruction in this section whenever this skill generates or substantially rewrites book content, even when the user provides no reference book. Use the Rust Book's general teaching methods: concrete problems, guided development, causal explanations, purposeful failures, gradual depth, revisiting ideas, and independent application. Write original prose and project-specific examples. Use the existing reader to present the content. These teaching requirements do not call for a reader redesign; the expandable code context specified under "Produce the HTML" is a required, focused addition to its code blocks.

Treat successful learning as the output: readers should be able to explain the program's behavior, diagnose a relevant failure, and apply a taught idea without copying the demonstrated solution. An accurate inventory of files, APIs, or commits is insufficient. Do not reduce the teaching requirements to a shorter tour just to save tokens. Spend detail on unfamiliar reasoning and meaningful changes; omit repetitive descriptions of already understood syntax.

### 1. Establish the audience and the learning contract

- Honor any audience, depth, scope, or learning goal the user specifies. Do not silently replace their request with a different course.
- If no audience is specified, write for an entry-level developer who understands variables, functions, and basic terminal use but is new to the project's language-specific features, domain, and implementation. State these assumptions in the book. Define language-specific syntax and domain terms before relying on them.
- Treat knowledge of ordinary variables and functions as a starting point, not knowledge of the language's syntax, references, compound types, or execution model. A construct is available for later reasoning only after its role and a concrete consequence have been established; mentioning its name or linking to its definition does not establish that knowledge.
- Do not assume that a reader has already studied the reference book or knows the repository. Introduce prerequisites that are essential to the project's behavior. When a prerequisite needs a separate course, provide a concise explanation and authoritative further reading, and identify the prerequisite plainly.
- Open with the concrete problem the project solves, who benefits, and an example of its visible behavior. Describe the starting point and the final result in ordinary language before presenting architecture or a large listing.
- Include a short reader contract identifying the intended audience, required knowledge, tools and versions, how to follow the lessons, and the limits of what the book covers. Explain the meaning of the example-state labels defined below.
- For a longer book that serves different learning preferences, give useful reading routes in the opening roadmap: follow the practical walkthrough, study the needed concepts first, or enter at a particular behavior. Name the prerequisites and specific sections for each route, and explain when to return to the main path. Use prose and existing links; a short book need not have multiple routes or new reader controls.
- Specify observable outcomes for the whole book. Use verbs such as trace, predict, explain, run, diagnose, compare, modify, and implement. Replace vague promises such as "understand the architecture" with a checkable ability such as "trace one input from the entry point to the output and explain where invalid input is rejected."
- Give each main lesson a specific learning outcome and a concrete question or problem that motivates it. Keep setup, reference material, and recaps proportional to their purpose rather than pretending each is a full project lesson.
- Keep planning categories out of the reader's path. A motivating opening can establish the outcome without an "Outcome:" label, and a direct instruction can establish placement without a "Location and action:" block. Use headings for meaningful changes in the reader's question, not for every function in the writer's checklist.
- Do not make readers answer optional audience questions before proceeding when a sensible assumption is available. State the assumption and continue. Ask only when missing information prevents an accurate or usable book.

### 2. Read the real behavior before designing the course

- Complete the evidence inspection above before drafting lessons. Trace at least one normal path and the meaningful failure paths through the actual project, including relevant configuration, dependencies, state changes, tests, and output.
- Identify the minimum set of concepts needed to explain those paths. Distinguish what the project uses from adjacent features the language supports but this book does not need.
- Create an internal source map: for each behavior or implementation claim, identify its supporting file, symbol, configuration, test, or historical change. Preserve the distinction between observed behavior, intended behavior, and the writer's interpretation.
- Use available history to explain real changes, but never assume that commit order is the best teaching order. Label a teaching reconstruction independently of historical facts. A hypothetical improvement is not an implemented feature.
- Identify what is difficult for this audience: unfamiliar syntax, ownership, asynchronous execution, state transitions, data representation, error propagation, configuration, boundaries between modules, or another evidenced source of complexity. Allocate explanation to those difficulties rather than giving every file equal space.
- Make an internal coverage map connecting the user request, relevant project behavior, essential concepts, lessons, and reader checks. For each main lesson, identify where its difficult concepts receive sufficient explanation and where its task receives explained feedback. A strong final or newly appended lesson cannot compensate for thin earlier lessons in a whole-book generation. When the request is only to append or revise a lesson, assess that lesson and its required prerequisites without silently expanding the edit scope. Include the important decisions and failure cases; do not inflate the course to cover unrelated language features or every private helper.
- Do not change project code, dependencies, architecture, or tests merely to create a cleaner teaching story. Put clearly labeled teaching variations in the book; preserve the checked-in project as the authority for its actual implementation.

### 3. Plan a progression based on prerequisites

Before drafting, make an internal lesson plan containing the following for each main lesson:

| Plan field | Required decision |
| --- | --- |
| Reader's starting knowledge | What can the reader already do or explain without help, based on declared prerequisites and preceding lessons? Do not count a concept merely because its name appeared. |
| Motivating problem | What concrete task, failure, limitation, or question makes this concept useful now? |
| Learning outcome | What should the reader be able to do independently afterward? |
| New concepts | Which unfamiliar ideas are essential, where does each first appear, what concrete value or behavior does it change, and which later step depends on that knowledge? Track ideas actually taught through a worked example and consequence; a mention, label, link, or expanded code line alone does not count. |
| Continuing example | What example makes the relationship visible with the fewest unrelated prerequisites, and what nearby variation will distinguish the rule from a plausible misunderstanding? |
| Development or explanation steps | What examples, traces, observations, and checks will establish the outcome? Include code changes only when they serve that outcome. |
| Misconception or failure | What plausible misunderstanding or failed approach should be examined? |
| Deferred details | What can wait, what is sufficient now, and where will the book return to it? |
| Reader practice | What task checks the outcome, how much guidance is appropriate at this point, which earlier ideas must the reader combine, where will explained feedback appear, and what restart or reset is needed? |
| Source support | Which project evidence supports the behavior and current implementation? |

- Sequence lessons so that each relies only on declared prerequisites or previously established concepts. Follow the reader's knowledge dependencies, not the filesystem tree or a list of imports.
- Derive the progression afresh from the declared audience and current project evidence, even when revising an earlier generated book. Reuse a prior book for reader-interface behavior and project evidence that still applies, but recheck each lesson dependency, example, task, and deferred concept; do not inherit the old order just because its prose or HTML is available.
- For readers new to the project's language, begin the code path, when feasible, with the smallest complete runnable behavior that establishes the entry point, output or other observation, enclosing syntax, and command needed to run it. Then add one useful relationship at a time, deepening the explanation and extending the behavior so the reader sees why the next concept becomes necessary. Keep future machinery out until then; a complete project listing does not explain its unfamiliar lines. If the project cannot be reduced to a standalone file, use its smallest runnable project action and make the required scaffold explicit.
- Balance concept lessons with practical application. Use a concept lesson to establish a rule or mental model; use a project lesson to combine established ideas in a working behavior. Do not prescribe a fixed chapter count or copy a reference book's sequence.
- Keep each development step focused on one meaningful behavioral or conceptual change. Several related syntax details may be introduced together when the change needs them; do not split a coherent idea into artificial fragments.
- When a step introduces several unfamiliar ideas, separate the explanation into understandable parts and identify the immediate purpose of each. Do not rely on a large unexplained listing as the introduction.
- Use clear, problem-oriented lesson and section titles. Prefer titles such as "Keeping the caller's value available" or "Rejecting an invalid input" to vague labels such as "Deep dive," "Implementation details," or "More features."
- Separate optional advanced material and reference material from the main learning progression. Introduce those sections as optional or reference-oriented in the prose so readers know when they need them. Keep essential explanations in the main path.
- Keep the plan internal unless the user asks for planning output. The book needs an intelligible roadmap, not the writer's process notes.

### 4. Match the teaching sequence to the lesson's purpose

A main lesson is a coherent unit with a shared learning outcome; it may contain several subsections. Its subsections can build toward one focused practice task and recap. Do not treat every heading or listing as a separate lesson requiring a repeated contract, exercise, and conclusion. If a subsection introduces an independent essential outcome, give that outcome its own check and feedback.

Every main teaching lesson must orient the reader, provide a concrete example and observation, explain the mechanism, check the intended understanding, offer practice with feedback, and consolidate the useful rule. These are functions of the explanation, not mandatory visible blocks. A connected passage can perform several functions, and a prediction followed by reasoned feedback can provide both a check and practice. Do not repeat the same task or add headings merely to display compliance. Choose the route below according to what the lesson teaches.

1. **Orient.** Connect to what the reader already knows and state the concrete problem and intended outcome.
2. **Provide an example.** Present a small example or current implementation that makes the question concrete. A development walkthrough may use a clearly labeled intermediate version. Use the project's actual behavior whenever possible.
3. **Observe.** Tell the reader what to run, inspect, or predict. Show the relevant output, state change, test result, or expected failure. Explain what the observation establishes.
4. **Explain the mechanism.** Trace what the program does and why the result follows. Supply the intermediate causal steps that this audience cannot infer: what operation receives which value, what it returns or changes, which branch uses that result, and why subsequent work can rely on it. Introduce the required vocabulary and syntax at the point they explain the observation. A list of definitions or a one-sentence paraphrase of each line does not satisfy this function.
5. **Change when needed.** In a development or repair walkthrough, develop the next version or correct the failure; compare alternatives when the lesson teaches a decision. State exactly what changed, why it helps, and what remains limited. A concept lesson explaining correct existing behavior may omit this function entirely.
6. **Check.** Use a focused command, test, trace, or prediction that checks the lesson's claimed behavior or rule. When code changes, choose a result that distinguishes the old and new behavior; when code stays unchanged, check that the reader can explain or predict it.
7. **Apply.** Ask the reader to predict, explain, diagnose, modify, or implement something related without merely recopying the example. Provide feedback as specified below.
8. **Consolidate and connect.** Restate the useful rule, identify the new ability, and connect the remaining question to the next lesson or later use.

For concept lessons, a correct existing example followed by a value trace, causal explanation, and prediction with feedback is a complete route. No broken first attempt, revised implementation, or before-and-after comparison is required. Use a counterexample or alternative only when it clarifies the concept. For project lessons, use incremental construction and checks at meaningful milestones. A lesson may combine these routes when its outcome needs both.

For setup lessons, emphasize prerequisites, exact commands, success indicators, and recovery from likely setup failures. For reference sections, emphasize definitions, contrasts, lookup examples, and links to where the material is applied. For short recaps, emphasize the gained abilities and the next problem when there is one. Do not manufacture code changes, failed attempts, alternatives, or unresolved questions to fill a template. This flexibility changes the teaching route, not the required depth of explanation, evidence, or practice in main lessons.

### 5. Develop examples through meaningful stages

- Select examples for the relationship they reveal, not merely their size or availability. Prefer project evidence that needs little unrelated domain knowledge or syntax. When a smaller teaching variation explains the rule more clearly, label it and reconnect it to the actual project. Choose related examples whose stable names, inputs, and behavior make the changed relationship easy to compare; include a nearby variation when it separates a correct prediction from a plausible misunderstanding.
- Prefer one recognizable project example across related explanations. Preserve its names, purpose, and input conventions so the reader can focus on the new idea rather than reconstructing a new scenario at each step.
- Start with the simplest version that demonstrates the immediate point. Show an actual limitation before introducing additional structure or machinery to address it. Do not declare an abstraction valuable without explaining the problem it solves.
- When the current code is too complex for a first introduction, use a smaller teaching reconstruction and label it as such. State what was omitted and reconnect the reconstruction to the current project version after the concept is established.
- Keep the behavior stable during a structural refactoring so readers can distinguish a change in organization from a change in functionality. When behavior changes intentionally, say what should now differ.
- Between successive listings, explain the exact changed expression, signature, data structure, branch, or responsibility. Identify what remains the same. Avoid the uninformative transition "now update the code" followed by a substantially different program.
- Use focused excerpts for local reasoning and complete listings at useful integration points: an early runnable milestone, the end of a multi-step feature, or a final view of how the pieces fit. Include an integrated runnable listing when otherwise the reader cannot connect fragments, locate their enclosing function or loop, or reconstruct the behavior being checked. Explain how the pieces relate around that listing; do not repeatedly print a large file after each small change or substitute a complete listing for its explanation.
- When a few lines need attention inside a larger example, keep the full source for that stage in the HTML and show a focused view with expandable surrounding code. Put a language-appropriate comment such as Rust's `// --snip--` at each hidden region. Explain this display convention once near the start of the book: the eye button reveals those lines, and copying gets the full code. The marker represents real lines hidden from view, not missing implementation. Do not use invented stubs such as "one input-and-comparison turn happens here" in place of available source.
- Explain whether the reader should replace a block, add a block, or inspect existing code. A short file caption and a direct instruction usually suffice. If the full context is unavailable or the lesson deliberately uses an incomplete fragment, label that limit briefly; do not invent surrounding code or offer a toggle that pretends to reveal it.
- Do not present a deliberately incomplete stage as runnable. Resolve required stubs and missing pieces before announcing a working milestone.
- Show how the final taught behavior maps to the checked-in project. If the pedagogical version differs, identify the difference and its purpose rather than silently claiming equivalence.
- Never imply that a reconstructed stage, experiment, or failed approach was performed by the original author without historical evidence.

### 6. Give every actionable code example a clear contract

Before or immediately alongside an actionable listing, give the reader the information required to use it:

- **Location:** the file, function, and relevant enclosing block or loop involved and, for terminal commands, the working directory. Distinguish file-scope definitions from statements that belong inside a function.
- **Action:** whether to create a file, replace its contents, replace a specific block, add a definition, modify one expression, or inspect existing code.
- **Prerequisites:** required imports, dependencies, configuration, input files, earlier code, and tool versions when they matter.
- **State:** whether it is a runnable example, a focused excerpt, an incomplete intermediate step, or an intentionally failing example. Use a short caption or an equally explicit sentence. Distinguish a compile failure, runtime failure, and logically incorrect output. Expanding a view does not make an incomplete stage or one file of a multi-file project independently runnable.
- **Execution or observation:** the command, input, test, or trace needed to examine the claim, including the starting state and any restart or reset between cases.
- **Expected result:** the important output, returned value, changed state, diagnostic, or success condition.

These details can be shared by consecutive examples when the location and context are unchanged; do not duplicate boilerplate around every three-line snippet. Establish stable display, copying, terminal, and evidence conventions once. Use a short caption to retain an example's state, and repeat an instruction or notice only when the state changes or omission would cause a specific misunderstanding. Do not explain a control in a paragraph and repeat that explanation in the adjacent caption. Prefer a caption such as `src/main.rs · Focused excerpt` and an instruction such as "Keep the secret number above the loop so each guess uses the same number." Avoid repeated warnings such as "not a complete runnable file" or "do not paste it over the source" when the caption, earlier convention, and surrounding code already make the use clear. Keep source versions and verification scope in concise source notes; mention them in teaching prose only when the current reasoning depends on them. Never remove a material limitation to make the prose smoother.

For a multi-step guide, establish one named practice workspace and use it for all teaching variations. Say once whether examples are created, copied, or reset there; later exercises should identify only the file and the state that changes. If platform-specific setup or restore steps are lengthy, put them in one concise setup note or appendix and refer back to it. Keep each lesson's actual code action, observation, and feedback in the main path. Never overwrite project source or omit a reset needed for a reproducible exercise.

- Explain terminal notation before using it. Distinguish commands, prompts, user-entered input, and program output. Do not make the reader infer whether a displayed line should be typed.
- Use shell commands appropriate to the intended reader's environment. Explain meaningful platform differences where they affect the instructions; do not add irrelevant operating-system branches.
- Keep enough enclosing structure visible to show where the focused lines belong, and make the other available lines expandable. Use a short filename caption and explain the action in normal prose. When a listing contains fragments from several locations, identify each placement; do not combine them into a pretend runnable file. Surrounding code must come from the same project version or clearly labeled teaching stage as the focused lines.
- Use the correct language tag and syntax colors for each listing: Rust code is `rust` or `language-rust`, not `javascript`. Distinguish terminal commands and output from source code.
- Explain each newly significant syntax element through its concrete role: what value or state it operates on, what type or relationship constrains it, what it returns or changes, and how the next operation uses the result. Do not leave these connections implicit behind terms such as "borrow," "result," or "shadowing." Do not describe already established punctuation repeatedly.
- When input conversion or branching is essential, show the actual or clearly labeled expected input/output first when that visible effect is the lesson's evidence. Explain it in ordinary words before using symbolic state notation. A trace does not substitute for visible output. Use escapes such as `\n` only when they help explain a later operation; define the notation before relying on it, and include platform variants only when they change the claim. Then trace a concrete successful input and relevant rejection through the actual sequence: raw value, normalization, conversion outcome, resulting value or binding, selected branch, and subsequent operations performed or skipped. Distinguish a terminal session from an illustrative trace. Apply this standard to the language and project at hand; it is not a requirement to discuss parsing in unrelated books.
- For temporary diagnostics or deterministic teaching changes, show the exact statement or replacement and its location, label the changed behavior, explain the expected observation and any remaining nondeterminism, and give the exact removal or restoration instruction. "Print the secret temporarily" is insufficient when the reader has not been taught how and where to do it. Keep the diagnostic separate from the final project listing.
- Walk through a manual checking sequence before publishing it. Track successful exits, failure exits, consumed input, modified files or state, and dependencies between cases. An input that wins or terminates the process prevents later inputs from being checked in that same run. Split independent cases into fresh runs, state precisely when to restart or reset, or provide a clearly labeled deterministic teaching variation. Never promise a later prompt after a branch that exits.
- Present output honestly. Distinguish observed output from expected or illustrative output. Do not fabricate a terminal transcript, compiler diagnostic, passing test, execution time, or benchmark result and label it as observed.
- For nondeterministic results, identify which parts may vary, what must remain true, and whether that variation affects the checking procedure itself, including early termination. If it does, specify a procedure that still checks every intended condition. A note that hints or timing vary is not enough. Do not promise identical random values, timing, network responses, filesystem paths, or thread-message ordering.
- Do not claim an excerpt was independently executed when only the full project was checked. State the actual verification scope when it matters.
- An intentionally modified teaching example may differ from the repository if the difference is explicit, technically valid for its stated purpose, and not misrepresented as current project behavior. Final project listings and actual-behavior claims must match the evidence.

### 7. Explain causes and consequences in a guided, approachable voice

Use calm, technically precise, everyday English. Address the reader as "you" for actions and observations. Use "we" naturally when reasoning or building together; choose it for a real shared step rather than applying a pronoun quota. Keep a conversational pace by accompanying the reader through the reasoning, not by adding jokes, stock encouragement, or a question to every paragraph. Do not imitate a reference author's distinctive phrases, persona, or examples. Internal planning may use specialist terms; translate them into accessible explanations in the book.

- Lead with the reader's task or an observable fact, then explain the mechanism, then the consequence. Introduce the technical name when it helps describe the mechanism. If a formal definition must come first, immediately ground it in a concrete use.
- Prefer familiar words and concrete verbs such as "gets," "stores," "returns," "skips," and "changes" when they accurately describe the operation. Say "the variable `number`" before relying on "the outer binding," and "the condition that must stay true" before relying on "invariant." Keep necessary technical names, define them beside a concrete use, and reuse them consistently. Do not replace precise distinctions with vague words or remove reasoning to make a passage shorter.
- At first use, establish the need in familiar terms, show the relevant expression, explain its immediate action on a concrete value, and introduce the technical name at the point it becomes useful. Translate unfamiliar syntax into a statement the reader can read aloud, then trace what it does here. For example, distinguish the text stored by an input call from the success or failure value it returns before presenting its full compound return type. For a reference passed to an operation, explain the access that operation needs first (for example, `&secret_number` gives `cmp` temporary read-only access to the other number); defer `Copy`, by-value, or preservation comparisons until later reasoning needs them. Several related syntax details can belong together; do not compress several new relationships into one definition.
- Connect sentences as well as paragraphs. Begin a new step from a value, operation, result, rule, or unresolved question the preceding text has established. Explain the relationship that carries the reader to the new fact. Shared subject matter or a connective such as "therefore" does not supply a missing premise. When changing focus, say what question is being set aside and why the new one matters now. Do not force every sentence into the same pattern.
- Connect paragraphs through the reader's developing expectation: recall what is known, show an observation that adds to or challenges it, and explain the revised rule. Make a plausible prediction visible before correcting it when that contrast teaches the rule. A comparison of familiar and unfamiliar cases can reveal a difference better than another definition. Do not invent surprises, misconceptions, or failures to force this route.
- Each explanatory paragraph should perform one useful job: orient attention, explain a cause, establish a rule, compare choices, resolve a misconception, or connect ideas. Follow dense explanations with an example or trace rather than stacking unrelated definitions.
- Explain why the current expression, type, parameter, branch, or module boundary is necessary. Connect it to the caller, data, output, failure, or constraint it affects. Distinguish what an API signature requires from a language guarantee, a policy, or a useful design choice. Check the implied alternative: do not say borrowing prevents losing a value when that particular value would be copied if passed by value.
- Replace inventory language with causal explanation. "This function has a mutable reference parameter" is incomplete teaching; explain what it may change, who still owns the value, and why the caller needs that arrangement. Follow a transformation or branch far enough that the reader can explain its effect on the next statement rather than merely repeat its name.
- Name the relevant identifiers and operations when ambiguity would force the reader to guess. Avoid chains of "this," "that," "it," or "the former" when several possible referents are present.
- Define unfamiliar terms in ordinary words at first meaningful use, then use the same term consistently. Do not define one unfamiliar idea through another untaught idea: "owned text" does not explain a string to someone who has not learned ownership. Establish the observable role first, and explain the extra relationship when it matters. Avoid cycling through synonyms for a domain concept merely to vary the prose.
- Distinguish terms that seem interchangeable but have different effects. Explain those differences through an operation or consequence, not only a glossary entry. Use focused language-specific contrasts where the code needs them: in Rust, mutability of a binding versus a mutable reference, borrowing versus moving ownership, success/error variants versus the value extracted from them, type annotation versus inferred conversion type, a match expression's supplied value versus a branch transferring control, a wildcard discarding details versus accepting valid data, and shadowing versus assignment. Teach only the relevant contrasts at their first use or recall their established explanation; these examples are a depth standard, not a mandatory Rust checklist for other languages or projects.
- Use short, direct sentences for instructions and more connected prose for reasoning. Vary sentence length according to the idea; avoid both clipped definition sequences and sentences packed with subordinate qualifications. Keep one recognizable example and its relevant values visible while explaining a relationship, so the reader need not reconstruct the situation between sentences.
- Use lists for ordered actions, alternatives, and checkable criteria. Use prose to explain why one step leads to another. Do not substitute bullets for the reasoning between code examples.
- Ask a rhetorical question only when the next demonstration or explanation resolves a real reader question. Do not fill the book with empty questions or unexplained prompts.
- Normalize difficulty in a specific way. Explain which unfamiliar relationship makes the topic challenging and how the next small step addresses it. Do not call difficult material "obvious," "trivial," "easy," or "just" to dismiss the reader's effort.
- After an error, treat the diagnostic as evidence about the code rather than evidence about the reader's ability. Use encouragement tied to a real completed task; avoid exaggerated praise and repetitive celebration.
- Use analogies only when they clarify a concrete relationship. State the relevant limitation when the analogy could lead to a wrong technical prediction. Return to the actual code after the analogy.
- Avoid unsupported superlatives, promotional writing, unexplained jargon, decorative introductions, and abstract claims such as "improves robustness" without identifying the failure it prevents.
- Do not prioritize brevity over a necessary causal explanation. Recall an earlier premise immediately before it enables a new deduction, even if the premise has already been explained. Remove repeated definitions, generic advice, and line-by-line paraphrases that add no understanding; do not remove a useful reminder merely because it is repetition.

Use the following original examples as a standard of explanatory depth, not sentences to paste into every book:

| Thin description | Required kind of explanation |
| --- | --- |
| "The function borrows the string." | "The caller still needs the text afterward. A reference lets the function read it while the caller keeps ownership. The function does not need to return the text to let the caller use it again." |
| "The parser returns a result." | "The text might not be a valid number. The returned value tells the caller whether conversion worked. The caller can then use the number, ask for another input, report the error, or stop." |
| "The loop retries on error." | "For invalid input, this branch skips the comparison and starts the next iteration. The prompt and read at the start of that iteration ask for another input. The comparison runs only after a successful conversion." |
| "The logic is moved into a module." | "The test can now call the function with chosen inputs, without reading command line arguments. It can check the returned value without starting the whole program." |

### 8. Control depth and revisit postponed details

- For every unfamiliar construct in an early example, decide whether the reader needs the full explanation to proceed, a useful explanation of its present role with deeper detail later, or a reference note outside the main path. Give essential reasoning first, add detail that strengthens the current model next, and move unrelated detail later. Do not give every page the same density or impose a fixed number of new concepts.
- When requirements compete for space, preserve the current reasoning and necessary action instructions first. Place adjacent mechanisms, alternative designs, boundary cases, and provenance where they become relevant or in a concise note. Full coverage across a lesson is not a reason to pack the entire coverage into its first paragraph. Expand at the point where the reader cannot yet make the next correct prediction; established operations can receive a shorter reminder.
- An operational explanation must state what the construct does in this example and what the reader must know to proceed correctly. "Ignore this for now" is not enough.
- Teach imports in layers. First show what an import enables at the call site and what that call does. Explain namespace, scope, prelude, or trait mechanics when they affect a prediction, a compile error, or a change the reader must make. Defer those terms until then, and include dependency-version details only when they explain a required command or observed behavior.
- If the full mechanism is deferred, say what remains to be explained and identify the later lesson that will explain it. Keep an internal list of those promises and resolve them before the book ends, or explicitly identify them as outside scope with appropriate further reading.
- Do not defer a fact the reader needs to predict the current result, understand a failure, or complete the current exercise.
- Keep an overview at the level it has established. Do not use an introductory behavior summary to justify an exercise that requires tracing syntax or branches taught only later. Essential code for a current explanation or task must be visible in its focused listing; expandable context is for supporting lines, not the missing premise of the lesson.
- Revisit important concepts in a changed context. Recall the earlier rule briefly, show how it applies here, and explain what the new situation adds. Do not paste the earlier explanation again.
- Where useful, improve an earlier working example after introducing a new concept. Explain why the earlier version was adequate for its lesson and why the new version is useful now.
- Make advanced sections deepen established ideas rather than introduce unrelated sophistication for its own sake. A short book can revisit an idea within a later section instead of creating additional chapters.
- Keep repeated naming and example conventions stable. If a later lesson changes them, explain the change and its purpose.

### 9. Teach failures and misconceptions deliberately

- For each main lesson, identify internally the most plausible misunderstanding for the intended audience. Address it in the text when it would change a reader's prediction, code, or choice. Do not invent a false belief merely to add a warning.
- Use a focused counterexample when it can reveal the rule better than another definition. Change one relevant condition where possible so the reader can see what caused the difference.
- For topics involving meaningful compiler restrictions, runtime failures, invalid input, or incorrect results, include a relevant worked failure and recovery when it teaches the outcome. Do not manufacture failures for simple setup or reference material.
- Label intentional failures before presenting them. Say whether the example should fail to compile, fail while running, fail a test, or run with incorrect behavior.
- Walk through the trigger, observation, cause, correction, and recheck when presenting a repair. Give the exact relevant input or code change, placement, execution context, and observation that reveals the cause. Identify the expression or assumption involved, explain why the correction satisfies the rule, and state the observation that distinguishes the correction from the failure. For a concept lesson about correctly handled rejection, explaining the existing branch and checking its behavior is sufficient; do not manufacture a repair. For an out-of-scope defect mentioned as a limitation, establish its cause and relevant trigger without claiming it was corrected.
- Show the relevant part of a diagnostic and interpret it. Explain the affected location, the important message, and any proposed correction. Do not dump a long log without helping the reader identify what matters.
- Explain the invariant in ordinary words: the condition the program relies on remaining true. Show how the invalid case violates it and how the corrected code restores or enforces it.
- Distinguish a compiler-enforced guarantee from application correctness. A compiling program may still implement the wrong rule, mishandle an allowed input, or leak resources.
- Distinguish anticipated failures from programmer mistakes when the project makes that distinction. Explain why the caller retries, returns an error, rejects a value, or stops instead of treating all errors alike.
- Do not teach readers to apply a suggested fix blindly. Check whether it preserves the intended behavior and relationships. When several fixes compile, explain which one satisfies the program's actual requirements.
- After correcting a failure, state what should now happen and why. If the demonstration remains incomplete, identify the remaining work rather than calling it fixed.
- If a diagnostic cannot be reproduced in the available environment, describe the expected category and cause honestly. Do not invent exact tool output to make the lesson look verified.
- Use evidence-grounded limitations and relevant boundary cases; avoid speculative warnings unrelated to the project or lesson.

### 10. Explain decisions through alternatives and boundaries

- For every important design choice covered by the book, state the concrete constraint, a plausible alternative, the benefit of the chosen approach, its meaningful cost, and the condition under which the alternative would be preferable.
- Compare approaches against the same requirement. Avoid giving the alternative an unfairly broken implementation merely to make the project's choice appear better.
- Where a staged comparison improves learning, let the reader see the simpler implementation's limitation before introducing the more structured one. Preserve the original project's facts when explaining a teaching reconstruction.
- Distinguish evidence about the author's decision from the writer's technical evaluation. Use phrasing such as "this design allows" rather than "the author chose this because" unless history establishes the motive.
- Separate a teaching simplification, the checked-in project's current behavior, and a production recommendation. A simplified example can be useful without being the correct implementation for every deployment. Distinguish language or mathematical correctness from an application's chosen rule and the clarity of its feedback. A useful hint can remain mathematically correct for a disallowed input; explicit rejection may improve feedback or enforce a stated policy rather than repair the calculation. State which consequence the change addresses and do not describe a usability improvement as necessary for correctness without a supporting requirement.
- State the boundary of each important simplification: what it omits, why that keeps the current lesson focused, the resulting limitation, and what would need to change if the omitted requirement became necessary.
- Do not hide missing validation, error handling, synchronization, or cleanup behind a general disclaimer. Explain the relevant limitation next to the example that depends on it.
- Do not change the project to remove a teaching limitation unless the user explicitly asks for an implementation change.
- For performance claims, distinguish theoretical reasoning, existing project measurements, and an actual benchmark run. State relevant inputs and limits of measured evidence. Never invent numbers or generalize a single measurement into a universal guarantee.
- Teach the reader how to decide in a related situation. Finish a substantial comparison with a usable rule of thumb and the circumstances that limit it.

### 11. Include practice that checks application, with feedback

Every main teaching lesson must include at least one focused reader task tied to its learning outcome and explained feedback for that task within the lesson or at a clearly identified answer location. Distribute these opportunities throughout the main lessons; an exercise in the last lesson does not establish that earlier outcomes were learned. Use an appropriate task; do not require all task types in every lesson. Short setup, reference, and recap sections may use a direct success check or relevant lookup instead of an artificial exercise.

| Task type | What to ask | What the feedback must establish |
| --- | --- | --- |
| Prediction | Predict a returned value, output, control-flow path, state transition, or failure before seeing it. | Give the result and trace the rule that produces it. |
| Explanation | Explain why an operation, type, check, or boundary is needed. | Give the essential causal relationship, not a restated definition. |
| Diagnosis | Locate and explain a focused defect or failed assumption in a clearly labeled variation. | Identify the cause, a valid correction, and the result that confirms it. |
| Modification | Change one behavior or requirement using the established concepts. | Define observable acceptance criteria and give a hint or worked solution when needed. |
| Comparison | Choose between two plausible approaches for stated constraints. | Explain the relevant benefit, cost, and conditions; acknowledge valid alternatives. |
| Transfer | Apply the concept to a different input, domain example, or small implementation. | State what a correct solution must preserve and how the reader can check it. |

- Plan increasing independence across the book. Begin with worked traces and focused changes when needed, then ask readers to produce a trace, locate a defect, choose an approach, or decide where a change belongs with less guidance. Match the help to the knowledge already taught; short books can make this progression within one lesson. Keep checking criteria and explained feedback available as assistance decreases.
- Include practice that combines earlier concepts at useful milestones. Ask the reader to identify and apply the relevant rules rather than naming every rule or supplying every step. The final independent task should be achievable from the preceding lessons, not a sudden jump in difficulty.
- Place prediction prompts before revealing their answer. Tell the reader to pause and make a prediction, then provide the explanation in subsequent prose. Do not require a new quiz interface or any frontend change.
- Keep exercises within the stated prerequisites and concepts taught so far. If a challenge needs a new idea, identify it as optional and supply the necessary background or a reference.
- Make a task require reasoning or a small independent action. Repeating the exact listing, reciting an API name, or asking "Did you understand?" does not establish learning.
- Use concrete inputs, expected behavior, and constraints. State the initial state and necessary resets so the reader can actually reach every observation. Check that a successful input, error, exhausted stream, or previous modification cannot silently prevent a later exercise step. Avoid vague tasks such as "improve the error handling" without saying what input or failure the new handling should address.
- Include a hint when a learner could otherwise be blocked by an unstated step. Offer the smallest clue that enables progress rather than immediately giving the complete solution.
- Provide enough feedback for self-study. Predictions and diagnoses need an explained answer. Implementation tasks need acceptance criteria and a checking method; include a reasoned solution or one valid approach when the criteria alone would leave the intended lesson unclear.
- Present solutions after the task, clearly identified in ordinary prose. Keep them in the existing content flow; do not add reveal controls, scoring, progress tracking, or new widgets.
- Explain why the answer works. For a likely wrong answer, explain the mistaken assumption when that contrast teaches the rule. Do not shame the reader or claim that only one implementation is valid when several satisfy the requirements.
- Reuse real project tests or deterministic examples when they directly check the task. If no suitable test exists, describe a small manual check or a clearly labeled book-only self-check without changing the repository.
- Include a final independent application appropriate to the book's scope: a small new behavior, a related use of a taught component, or an explained design choice under changed constraints. Provide acceptance criteria. A small project need not acquire a large capstone.

### 12. Make hidden relationships visible through content

- Use a compact table, text diagram, annotated listing, or step-by-step execution trace when prose and code leave an important relationship hard to see. This is instructional content, not permission to redesign the reader or add visual libraries, controls, CSS, or frontend behavior.
- Choose the representation for the difficulty: a value trace for transformations, a relationship diagram for ownership or module boundaries, a transition table for states, or a timeline for concurrent operations.
- For a value trace, include the step, relevant expression or operation, current value or type, selected branch where relevant, and consequence. Mark any newline, whitespace, encoding, or platform difference that changes the observation; do not assume a line terminator is present on every input. Show only the values needed to explain the outcome and distinguish observed from illustrative values.
- For ownership or reference explanations, identify the owner, the referenced value, relevant scope or lifetime, and what changes when a call or scope ends. Keep the explanation consistent with the actual language rules.
- For asynchronous or concurrent behavior, distinguish guaranteed order from a possible execution. A diagram of one scheduling outcome must not imply that every execution has that order.
- For a state transition or control-flow diagram, identify the starting state, triggering operation, actual destination, and any rejected transition or exit. Trace every arrow back to the code. Separate paths for rejection, an ordinary retry, a successful exit, and end of input when those paths exist. Show which operations repeat, which are bypassed, and which local state is recreated. A retry that prompts and reads again must point to that actual start of the next iteration; it must not appear to return directly to parsing the old input. In a finite-input loop, show advancing to the next item and exhaustion rather than implying another keyboard read. Explain how code or types enforce the depicted rule.
- Keep related diagrams, traces, and tables consistent across stages: reuse names, arrow meanings, boundaries, and viewpoints unless a change is explained. Show what changed and what stayed the same so the reader can compare states. Distinguish an arrow for ownership, access, or control flow; do not let the same mark silently acquire another meaning. A useful sequence may compare a predicted relationship with the actual one, clearly labeled. No illustration quota or reader redesign is required.
- Introduce each representation by stating the question it answers. Explain the significant relationship afterward and reconnect it to the code.
- Keep representations accurate, small, and useful. Omit diagrams that simply repeat a nearby sentence or serve as decoration. Do not add an illustration to satisfy a quota.

### 13. Consolidate, connect, and teach further investigation

- End each main lesson with a concise recap of the rule, the behavior it explains, and the ability the reader has gained. Do not merely list the identifiers introduced in the lesson.
- State a concrete unresolved question or limitation when it motivates the next lesson. Avoid generic transitions such as "next we explore more advanced topics."
- When an important earlier idea returns, name its connection and point to the relevant lesson. Avoid requiring the reader to remember a distant explanation with no reminder.
- At an integration milestone, trace the complete behavior using the pieces already taught. Explain how their responsibilities connect rather than repeating all local definitions.
- Teach readers where to investigate unfamiliar APIs, diagnostics, or configuration: authoritative API documentation, command help, project tests, or a specific guide. Explain what question the resource will answer.
- Link to specific relevant documentation rather than a large collection of undifferentiated links. Do not outsource the explanation of an essential concept to an external page.
- Put supporting syntax tables, a glossary, command reminders, or version details in reference-oriented sections only when they help this book. Keep the definitions consistent with the main explanations and connect them to examples.
- Finish the book by checking its promised outcomes against the completed examples and independent task. Identify remaining limitations and a relevant next learning step without claiming mastery of the whole language from one project.

### 14. Review teaching quality before finishing

Conduct this review in addition to the HTML and evidence review below. Revise the content until every applicable criterion passes. An exception must have a specific reason connected to the section's role, the user's scope, or an unavailable verification environment; it cannot be justified merely by saving time or tokens. Passing format validation or compiling a program does not establish explanatory depth, accurate diagrams, usable exercises, or good teaching. Review the actual text and its observations against the criteria. Keep internal planning and audit notes out of the book unless the user asks for them. Report material factual or verification limitations honestly.

**Book-wide review**

1. The audience, prerequisites, scope, tools, example conventions, and intended outcomes are explicit and mutually consistent.
2. Each essential concept is introduced before a lesson depends on it. Optional advanced material is identified and does not interrupt the main progression.
3. The lessons explain the actual normal and meaningful failure paths, not merely a file inventory or chronological list of commits.
4. Current project facts, actual historical changes, reconstructed teaching steps, hypothetical improvements, and technical evaluations are distinguishable.
5. The book shows a coherent progression from an initial behavior or problem to integrated understanding and independent application.
6. Important concepts return in a relevant new context; promised later explanations are delivered or explicitly placed outside scope.
7. The book's length and density follow the learning need. Essential reasoning is not compressed away; reader-facing wording uses familiar words and defined technical terms. Each difficult passage has an identifiable chain from established knowledge to the new relationship and its consequence. Repeated contracts, notices, control explanations, definitions, exercises, unrelated features, and generic filler are removed. Useful reminders preserve the premises needed for new deductions. Alternative reading routes include prerequisites when the book needs them.
8. Original wording and project-derived examples are maintained throughout. General teaching methods do not become copied prose, a copied chapter sequence, or a borrowed visual identity.

**Main-lesson review**

9. The lesson has a concrete motivating problem and an observable learning outcome.
10. A reader with the declared starting knowledge can follow the intermediate causal reasoning from new syntax through relevant values, types, state, ownership, and control flow to the outcome; when code changes, the reader can also explain each meaningful change and why it is made. The text establishes how to read unfamiliar expressions and what concrete values they operate on before combining them. When familiar syntax returns with a different job, the changed role is explicit and a concrete value is traced through it to its later use before finer explanations rely on that role. Named concepts, plain words, and one-line descriptions alone do not pass.
11. Observations, outputs, or checks establish the lesson's claims; concrete success and relevant rejection traces explain essential transformations and identify later operations performed or bypassed. Any platform-dependent or illustrative part is identified.
12. Difficult concepts receive causal explanation, useful contrasts, and the relevant misconception or failure when needed. The example reveals the intended relationship without avoidable prerequisites. Its explanation connects the reader's prior expectation to the observation and useful rule, using sentences this audience can follow.
13. Important choices state their constraints, benefits, costs, alternatives, and limits without inventing author intent. Correct calculations, application policies, and clearer feedback are distinguished; improvement claims name the actual consequence.
14. Every main teaching lesson in scope has a focused task checking its shared outcome, with explained feedback accessible to a self-studying reader. Subsections may contribute to the same task without repeated ceremony; independent essential outcomes remain checked. Practice gradually asks the reader to make more decisions and combine earlier ideas. A well-developed final lesson does not excuse missing explanation or practice earlier.
15. The recap identifies the learned rule and new ability; a transition explains the next relevant question when there is one. Concept lessons are not padded with invented repairs, alternatives, or before-and-after comparisons.

**Example and exercise review**

16. Every actionable example supplies its location and enclosing context, action, prerequisites, example state, checking method, starting state, and expected result. Short captions and shared context avoid repetitive disclaimers. Fragments from different locations are distinguished; an integrated runnable listing is included where needed to connect them. Temporary diagnostics specify their exact addition, observation, and removal.
17. Listings, language tags, types, identifiers, commands, inputs, explanations, traces, and outputs agree. Teaching variations are labeled; actual-behavior examples match the project. Focused and surrounding lines belong to the same source version.
18. Intentional failures are announced before the code, with enough context to reproduce the relevant observation. Repairs explain trigger, observation, cause, correction, and recheck; correctly handled rejection and out-of-scope limitations do not acquire invented code changes to fill that sequence.
19. Required intermediate gaps are resolved before a milestone is described as working. Display omissions reveal actual source rather than placeholders; focused excerpts use the required context toggle when full surrounding code is available. Truly incomplete fragments remain clearly labeled.
20. Observed and illustrative results are distinguished. No execution, passing check, benchmark, diagnostic, or historical experiment is fabricated.
21. Exercises and manual checks use established prerequisites, explicitly ask for an independent action or prediction before showing feedback, and include usable acceptance criteria and an explanation of the result. A worked table or already-shown answer does not itself make a task. Their ordered steps remain executable despite successful exits, errors, randomness, exhausted input, or state changes; required restarts or resets are explicit.
22. Each instructional table, diagram, or trace agrees with the actual code and supplies an unambiguous destination for every depicted branch or arrow. Retry targets, repeated reads, recreated state, skipped work, exits, and possible ordering are accurate where relevant. Related representations keep their names and notation consistent or explain changes. It introduces no reader-interface or frontend requirement.

Finally, perform an internal reader walkthrough from the beginning of the content in scope. At every point, ask: "What can the reader explain using only the declared prerequisites and preceding text? What are they being asked to do? What should they observe? Why does that observation follow? Does the process or state still permit the next requested check?" Track the learner's workspace as well as program state: know what the practice copy currently contains, not just which source excerpt is visible. Showing an excerpt does not edit a file. Before a run or exercise that needs a different version, give the exact reset or edit at the point it becomes necessary. Do not credit a concept as learned merely because it appeared earlier. For each task, trace every required operation back to the preceding example and explanation that establishes it; a term mention, glossary entry, link, complete listing, or expandable line does not establish usable knowledge. Reject technically accurate but compressed prose at its first unsupported inference. Stage the example or add the missing causal bridge before the reader is asked to use that idea. Trace each ordered checking procedure, including what happens after a win, error, or end of input; add a fresh-run instruction or revise the procedure when necessary. Repair any step that requires guessing an unstated prerequisite, code location, transformation, or result.

Then perform a separate prose revision, using the passage-revision model. Read every main explanation in order, especially first introductions, paragraph boundaries, and the prose between listings. At the first unsupported inference, identify the exact sentence, the knowledge established so far, and the missing relationship. Repair it by recalling a needed premise, showing a concrete value, translating syntax, supplying the causal step, or moving an adjacent detail to its proper place. Re-read the preceding and following paragraphs after the repair. A paragraph is not accepted merely because all its facts are accurate or its vocabulary is simple. The reader must know why the next sentence follows and which question is being answered. Remove writer commentary that narrates the teaching method where the reader needs the mechanism instead (for example, "we needed to see the change to know what the type is for" or "after the example we can name the mechanism"); replace it with the concrete relationship. A short signpost may orient the reader, but it does not count as an explanation. Remove visible checklist ceremony and redundant notices without removing action instructions, feedback, accurate example labels, or material limits. Preserve natural variation; this is a comprehension check, not a sentence template or a requirement to manufacture revisions when a passage already works.

Verify the smallest representative runnable example or exercise expectation needed to substantiate a material claim, using an isolated practice location for book-only variations rather than changing project source. Review the explanation and feedback as well as the execution result, and check whether the reader can complete the final independent task using only established knowledge. Recheck technical meaning after prose revisions: smoother wording must not invent a guarantee or change an API's behavior. Resolve gaps before returning the artifact; if the environment prevents technical verification, identify the precise unverified claim rather than implying that the check passed. One passing trial is evidence about that trial, not a guarantee of identical quality on future invocations.
